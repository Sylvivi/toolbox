# 云同步与收藏模型

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **⚠️收藏模型「明明选了却提示没选」＝中转站编号过期 + 静默失败（2026-07-28 修）**：用户在阅读模式从收藏里选模型，界面显示已选中，一点「讨论」却弹「请先选择模型」。她自己的描述直接指到病根：**「我选的是一个，但实际选中的有可能是另外一个」**。根因：收藏条目记的是中转站**内部编号 `providerId`**，而**删掉再重新加同一个中转站编号就变了**（空号）；`sel.value = 不存在的编号` 是 **DOM 的静默失败**——下拉框变成空白、不报错不抛异常。老 `chatPickFavModel` 切完不检查，后面照样写 `chatSelectedModel`、点亮发送键、把标签改成那个模型 → **界面显示已选好、实际中转站和密钥都是空的**，`readingAskOne`/`readingCommentOne` 那道 `if (!item || !chatSelectedModel)` 闸就报「没选模型」。
  - **⚠️提示语冤枉了模型**，所以她怎么重选模型都没用——现在 `chatNoModelMsg()` 分两种说：中转站没选中就点名中转站。**这类「A 坏了却报 B」的提示是最贵的**：她会顺着错误的方向反复试。
  - **修法**：`chatFavProviderId(fav)` 先按编号找、找不到**按 `fav.url` 兜底**（网址是中转站的稳定身份，改不了）——`chatResolveCompressModel` 早就是这个顺序，收藏这里当初漏了。**都找不到就提示「XX 已经不在了，去密钥页重新收藏一次」并直接 return，绝不假装选好**。
  - **⚠️顺手拆掉写死的 `setTimeout(…, 100)`**：老代码用它「等模型列表加载完再选中」，其实 `onChatProviderChange` 里动 `chatSelectedModel`/`chatSelectedKeyStr` 的几条路（`onChatKeyChange`/`chatLoadModelsForCurrentKey`）**全是同步的**，只有 `chatFetchModels` 异步且不碰选中的模型。赌网速的等待纯属隐患。
  - **⚠️⚠️但这不是她遇到的那个——用户当场否掉了「中转站过期」这个结论（「我觉得不是中转站的问题，应该是功能上的问题，它没有过期」），她是对的**：`chatRenderFavSection` 每次渲染**本来就会按 url 自愈 providerId**，而她正是从收藏区点的，编号早被修好了。**教训：找到一个「能解释症状」的 bug ≠ 找到她那个 bug；用户说「不是这个」时先信她、回去继续查。** 继续查出来的三个真问题（2026-07-28 同日修）：
    - **① 模型和中转站没有一起还原（最可能是她那个）**：`readerOpenChapter` 记下并还原 `chatSelectedModel`，**中转站的下拉框却一个字没管**；只要它在别处被清空过一次（`chatLoadConv` 里 `if (conv.providerId)` 为空时那整段还原被跳过），之后就是**模型一直有、中转站一直空**，怎么重选模型都没用。现在开章时中转站也一起还原（`_rconv.providerId → chat_last_provider`，只认下拉框里真有的那一项）。**铁律：模型/中转站/密钥这三样，谁都不许单独还原。**
    - **② 收藏区按「中转站名字」分组**：注释写着「不同站点绝不混排」，实际 `groups[fav.providerName]` ——**两个同名的中转站会被并进同一组**，她点的那一行其实属于另一个站（正是「实际选中的有可能是另外一个」）。改成按 `getBaseUrl(fav.url)` 分组，名字只当组标题显示。
    - **③ 收藏区标题的「当前:」会瞎猜**：精确匹配（站+模型）失败后**退回只按模型名找**，于是显示成**另一个站的同名模型**。改成只认精确匹配，宁可不显示「当前:」；中转站空了则显示「⚠️ 没选中转站」——**界面必须让「坏掉」看得见**。
    - **④ 自愈 `chatEnsureProvider()`**：讨论/点评/标背景/翻译四个入口在报错前先调它——中转站空了但模型还在时，按「这个模型属于哪个站」把中转站切回来并弹一句「已自动切回 XX」。⚠️**只在能唯一确定时才切**（收藏里有且只有一个站收藏了这个模型；否则退回 `chat_last_provider` 且它上次用的就是这个模型），**认不出就老实报错**——猜错＝请求发去别的站、扣别人的钱。用户自己选的「自动找回来 + 告诉我」。
  - **排查心法**：先在无头浏览器里**把她的症状复现出来再动手**（`tests/favmodel.test.js` 的 B 组就是那次复现脚本转成的）——这次一跑就看见「显示的模型=claude-y / 中转站=(空) / 弹没选模型=true」，比读十遍代码都快。
  - 测试 `tests/favmodel.test.js`（18 条）。

- **云同步架构（CF 主力）**：CF 走「逐卡片 + 清单(manifest)」（`cfBuildManifest`/`cfSmartSync`），**整包 blob（`buildSyncPayload`）只给 Gist 和本地快照用，CF 不碰**。想让某项数据在 CF 同步，必须挂进 **manifest**、不能只塞 blob。密钥/收藏夹逐卡片（`k_`/`s_` + `cardTimestamps`）；书签、字体、阅读进度、收藏模型等「整块按时间戳后写覆盖」（能正确传播删除）。

- **⚠️对话记录是同步的，别再被那句过时注释骗了（2026-07-31 记）**：`exportAllData` 里那句「共读/对话记录与阅读书库不参与云同步」**早就过时**，对话云同步是后来加的。**云端结构跟别的数据完全不同**：不进 `_manifest`，而是①一个对话一条 `chat_<对话id>`；②**自己的清单** `_chat_manifest`（`{chats:[{id,title,model,updated,msgCount,pinned}]}`）；③超过 `CF_CONV_PLAIN_MAX`(1.4MB) 自动切块 `chat_<id>::p0..pN`（绕 D1 单行 2MB 上限），读时拼回。所以**用 `chat_history`/`convs` 去 grep 或探云端键，一个都探不中**（那是本机 IndexedDB 的键名）——实测在用户云端捞到 27 个对话，含 244 条消息的「翻译窗口」。相关：`chatSyncPush`/`chatCloudPull`/`cfPutConv`/`cfGetConv`，防缩水（云端条数多就不推）、删除走 `chat_tombstones`(30 天)。**教训**：注释和代码打架时以代码为准；用户说「明明能」的时候，先按她说的去找，别拿注释当证据反驳她。

- **收藏模型同步（2026-06-20 修）**：`chat_fav_models`（含每模型备注/价格 `f.price`）经 `chatFavModelsSave()`（写本地+盖 `_ts`+防抖 `syncPushData`），挂进 `cfBuildManifest`、按 ts 覆盖。**单价存在收藏对象里，收藏一同步计价价格就跟着同步。**

- **⚠️阅读进度（`reader_pos`）从来不推云端，只能等别的数据顺路捎（2026-08-09 修）**：用户报「两边页面都开着的时候，在一边产生了读痕，如果要同步到另一边，总感觉好像需要触发点什么，有时候碰巧能触发，有时候就怎么也触发不了，刷新也不太能解决」。**症状描述就是病根**：`readerSetProgress` 原来只 `localStorage.setItem`、**一句 `syncPushData` 都没有**。`reader_pos` 明明挂在 manifest 里，所以只要**别的**东西推一次（划线 `readingSaveAllHl`、书签 `readingSaveAllBookmarks`、提问、签到…都自带推送），进度就被顺路捎上去了——「碰巧能触发」是这么来的；「怎么也触发不了」＝这一趟纯看书没碰别的。
  - **⚠️拉取那边一直是好的，别往那儿查**：`autoSync` 每 30 秒一轮，外加 `visibilitychange`/`focus`/`pageshow` 都拉。**所以刷新救不回来——云端压根没有新数据**。用户说「刷新也不太能解决」时，这句话本身就在排除拉取侧，要听进去。
  - **修法**：`readerSetProgress` 末尾加防抖推送。**⚠️防抖必须比别处长（8 秒，别照抄书签的 3 秒）**——滚动停 150ms 就存一次进度，看书时一直在存，短防抖会把同步接口打爆。
  - **⚠️真正保命的是 `flushReaderPosPush`**：`visibilitychange`(hidden) + `beforeunload` 时立刻把欠着的推出去。**换设备的那一刻正好触发这两个事件**，没有它，8 秒的债在「读完就切电脑」这个最常见的场景里永远还不上。照搬签到 `flushCheckinPush` 那套。没欠债时不白推（`_readerPosPushTimer` 为空就 return），免得每次切标签页都打一发。
  - **合并规则没动、本来就是对的**：`cfPullData` 里逐本书按条目内的 `ts` 取较新的，两台设备读不同的书不会互相覆盖。
  - **教训**：manifest 里挂了字段 ≠ 这份数据会同步。**挂进清单只解决"推的时候带上它"，不解决"谁来触发推"**——每个写入点都得自己排推送。查这类「有时灵有时不灵」先列出该数据的所有写入点，逐个看有没有跟推送。
  - 测试 `tests/readerpossync.test.js`（13 条）。

- **⚠️⚠️问答/背景「同步过来了却不显示」＝渲染缺口，不是同步坏了（2026-08-09 修）**：用户报「两边页面都开着的时候，在一边产生了读痕（问答、背景知识那些），如果要同步到另一边，总感觉好像需要触发点什么，有时候碰巧能触发，有时候就怎么也触发不了，刷新也不太能解决」。**这条跟同日修的 `reader_pos` 是两回事，别混**：`reader_qa` 的推(`readerPersistQA`)和拉(`readerMergeByChapter`)一直都是好的。
  - **病根**：`readerHydrateLoadedQA`（把同步来的问答重灌回正文快照）这个函数早就写好了、注释里连症状都描述对了，但它**全项目只在 `chatLoadConv` 里被调过一次**——只有「打开这本书的会话」那一刻才灌。页面已经开着时，autoSync 每 30 秒确实把云端问答并进了 localStorage，**屏幕上那份正文快照没有任何人去动**，于是必须退出去再进来才看得见＝她说的「需要触发点什么」；「碰巧能触发」＝她刚好切走又切回来。
  - **「刷新也不太能解决」也在这儿**：刷新后会话常常在拉取回来**之前**就渲染完了，数据到了同样没人重灌。**用户这句话是有信息量的线索，别当成"她记错了"**。
  - **修法**：新增 `readerApplyPulledQA()`，在 `cfPullData` 合并出变化后当场调。**只重渲 content 真的变了的那几章**（重渲会动到开着的提问条和阅读位置，无脑全刷代价太大），重渲一律套 `_rdKeepScroll`（复用标背景那边已解决的「插入在视口上方会把正在看的那行顶跑」）。
  - **⚠️`chatStreaming` / `readerBgRunning` 时一律不插手**：那两个过程自己在改 `content` 并逐条重渲，掺一脚等于两边抢同一块 DOM；它们跑完后的下一轮 autoSync 会补上。
  - **教训（跟 `reader_pos` 那条合起来看）**：一份数据要真正「跨设备可用」要过四关——**写入点有没有推 → manifest 带没带 → 拉取有没有合并 → 界面有没有重灌**。这两次分别栽在第①关和第④关，而中间两关一直是好的。查「有时灵有时不灵」就按这四关逐个走，别一头扎进同步代码。
  - 测试 `tests/qapullrender.test.js`（14 条）。⚠️写这类测试**假书每章要有足够多段落**：问答按 `[P段号]` 挂在具体某段下，段号在正文里不存在就"数据灌进去了、屏幕上渲不出来"，第一版每章只写一段，那条断言假挂在这儿。

- **⚠️⚠️「读痕少的会盖掉多的」（2026-08-09 修，用户自己看出来的：「似乎会让读痕少的覆盖多的，这对吗」——对）**：`readerPersistQA` 写的是**整章一格**，合并时也是**整格按时间戳替换**，也就是「这台设备当前视图里的那一章」＝它广播给全世界的真相。于是：手机第 5 章有 3 条问答并已推送 → 电脑也开着这本书但还没拉到（30 秒窗口内，**或正在流式回答/标背景所以被 `readerApplyPulledQA` 的守卫跳过重灌**）→ 在电脑上问了 1 个问题 → 电脑打包写「第 5 章＝1 条」且时间戳更新 → 手机拉下来整格替换。**3 条在两台设备上同时消失，救不回来。**
  - **修法**：写之前跟本地存的那一格做**并集**——视图里没有、但本地存过的条目一律保住。那种条目的含义只有一个：这台设备还没把它同步进视图，**不是用户删了它**。
  - **⚠️唯一允许"变少"的是明确的删除**：`readingDeleteBlock` / `readingRegenBlock` 把被删条目的身份（`_qaOfComment` → `{p, q}`）经 `opts.removed` 传进来，只有它被排除在并集之外。**这条护栏最容易矫枉过正成「删了又自己回来」**，`tests/qapullrender.test.js` 的 F 组专钉这个（F2 还钉了「删一条的同时别处同步来的那条仍在」，两条规则必须同时成立）。
  - **⚠️`_qaOfComment` 取 q 的算法必须跟 `readerPersistQA` 里那段逐字一致**（剥「汐：」前缀、取第一行、trim）。两边一旦有出入，删除就对不上身份、被当成缺失补回来。
  - 并集后按段号**稳定排序**（视图里的在前、补回来的在后），否则渲染顺序会跳。
  - **这不是"同步冲突"的通用解**：真要彻底，得做逐条墓碑。但那要改存储结构；现在这套（并集 + 明确删除带身份）把用户真正会遇到的「同时读同一本书」这个场景堵死了，代价小得多。

- **⚠️⚠️划线/读痕的「删除墓碑」（2026-08-13 做）——上一条说的"逐条墓碑"，在这里补上了**。
  - 用户报「**划线删除之后为啥还会自己回来呀**」。根因：划线和读痕走**逐会话取并集**（`_mergeMarksBlobs` → `_readerMergeMarks`），本地删掉一条、云端那份还在，下一次同步就并回来；而同步是**先拉后推**，并回来的那条紧接着又被推上去 → 删除被彻底抹平。**不是偶发，是必然**——只要云端有旧副本，删除就一定会被撤销。
  - **并集不能去掉**（它挡的是上一条那种真丢数据），所以补墓碑：`reading_marks_tombs`＝`{id: 删除时间}`，**划线和读痕共用一张表**（两者 id 都是「时间戳-随机串」不会撞，且共用同一个合并函数，分两张表只会多一份忘记同步的风险）。结构和过期清理照抄对话那套 `_chatGetTombstones`，**别自创第二种写法**。
  - **⚠️碑要 90 天，不是对话那套的 30 天**：书是慢慢读的，一本搁两个月再打开很正常；碑过期太早，那台设备一开机就把早删掉的划线又并回来了。
  - **四个地方缺一不可**，漏任何一个都会以不同形式复活：
    1. `rdHlDelete` 里**先立碑再存**（`rdMarksTomb`）；
    2. `_mergeMarksBlobs` 合并完按碑筛一遍——⚠️**剔掉了东西要算 `changed`**，哪怕条数跟本地原来一样：`changed` 触发「把本地这份回推上去」，云端那条才真正消失，否则每次同步都要白剔一遍、碑一过期就复活；
    3. 碑挂进 **manifest**（`marksDeleted`）——不同步的话，另一台设备（它没有碑）会把它本地还留着的那条又推上来；拉取时**双向取并集、只进不退**（两台设备各删各的，按时间戳覆盖会把对方的碑抹掉）；⚠️**墓碑必须在合并划线之前跑完**，顺序反了表现是「删掉的东西闪一下又出现」；
    4. `cfGetManifest` 那条**整包覆盖写入**的路径（新设备/重新登录）不经过 `_mergeMarksBlobs`，得单独补一次设碑 + `rdMarksSweepTombs()`。
  - **`rdMarksSweepTombs`（全表清扫）为什么必须有**：`_mergeMarksBlobs` 只遍历**云端有的**会话键。别的设备删掉一条、碑同步过来了，但云端恰好还没有这本书的划线数据时，这台设备上那条就扫不到、一直留着。
  - **⚠️最危险的是矫枉过正**：只许剔「碑上有的」，多删一条就是「同步会吃掉别的设备的划线」，比原来的 bug 严重得多。`tests/hltomb.test.js` B 组专钉这个（别人新划的原样并进来 + 一条都没多删 + 没有碑时一条都不动），17 条全绿才算过。

## 2026-09-06：搬到自建后端，GitHub Gist 整个删掉
