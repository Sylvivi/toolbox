# 界面·手势·渲染杂项

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **⚠️「汐」在代码里是两种身份，别顺手统一（2026-08-02 加昵称功能时理清）**：用户的朋友也开始用这个工具了，所以昵称做成可改（设置面板「昵称」栏 → `chatUserName()`，存 `toolbox_user_name`、走 CF 同步）。**但只有「给人看的名字」跟着昵称走**（AI 称呼、问答气泡、读痕面板、导航面板，7 处）；**`QA_TAG='汐：'` 是存储格式标记，一个字都不能动**——正文问答以 `[P3] 汐：问题` 存进 `msg.content`/`reader_qa`，二十来处 `/^汐：/` 靠它认出「这块是问答不是点评」。改掉它的后果是**静默的**：正文照常显示，只是双击不再走追问、摘要开始把闲聊当剧情压进去、读痕面板捞不到问答，几千条历史问答集体退化，要等用到那个功能才发现。所以改昵称是**纯显示层**的事，不迁移任何数据、改回去也一样。发给 AI 的副本用 `chatQaTagToName()` 把标记换成昵称（否则系统提示说用户叫小明、上下文里一堆「汐：」，AI 以为是第三个人）——⚠️**它的正则必须连 `[Pn] ` 段号前缀一起吃**，第一版只认行首、一条都没替换到，测试逮到才发现（真机上看不出来，只表现为 AI 偶尔管你叫汐）。云同步判在不在用 `!== undefined`，**空串是合法值**（＝用回默认），真值判断会让「改回默认」永远传不出去。测试 `tests/username.test.js`（23 条）。**顺带记下**：`READING_MODE_DEFAULT_PERSONA` 里还有 228 字男生子题材声明 + 186 字家族树画法，那是用户自己的口味，别人用要自己在系统提示词框里填内容覆盖掉（框里非空就不走兜底人设）。

- **右滑返回手势（2026-07-29 抽成公用）**：`attachSwipeBack(el, canStart, onBack)` —— **从屏幕左半屏起手、往右划够 80px** 触发，左边缘冒一条主题色提示。聊天面板（对话→列表→退回标签页）和书架面板（**目录 → 书架(文件夹内) → 文件夹列表 → 关掉**，用户要求文件夹也算一层）共用这一个函数，手感参数只有一处。⚠️`dx<0` 或竖向偏移 >60px 立刻放弃——**误触发（滚正文时面板自己关了）比"滑不动"贵得多**，`tests/swipeback.test.js` 的 B 组专钉这条。⚠️判「在不在目录里」看 `#rbChapterView` 的 display、**不看 `rbActiveBookId`**：远程占位书下载中/失败时 id 已有值但界面还在目录。⚠️提示条是全局共用的一个懒创建节点，别改成每个面板各建一个。**写这类测试要先造两本假书**：`rbRenderShelf` 在书架为空时会把 `rbCurrentFolder` 重置成 null，空书架下文件夹那层根本不存在，会假阳性地"少退一层"。

- **三模式选择器**：`对话 / 翻译 / 共读`（无 emoji），分段按钮，互斥。`chatSetMode()` / `chatSyncModeButtons()`。默认打开固定显示**密钥页**（`init` 里 `savedTab='keys'`，不再恢复上次标签）。

- **翻译模式追问**：长按译文块触发（约 0.5s，移动超 10px 取消），双击/拖选留给浏览器选词复制。

- **等待中可中止**：翻译、翻译追问、共读提问加载时按钮带 `✕`，用 `AbortController` 掐断；中止不弹报错。

- **遮罩**：`chat_mask` localStorage（'1'/'0'）控制 `body.chat-mask-on`，初始化按保存值强制对齐。

- **夜间模式**：clawd「主题」子面板 🌙 开关（`setNightMode`，存 `toolbox_night`）。每个浅色皮肤有 `.theme-xxx-night` 类，**7 个夜间皮肤共用同一套深蓝底**，只强调色不同；`深林绿(dark)` 无夜间版。`applyTheme` 里 `cls = (nightMode && t.night) ? t.night : t.cls`。
- **🎲 随机主题（2026-08-08 补入口）**：长按 + 号的主题小窗第一行。**存两个键**：`toolbox_theme` 存占位串 `'random'` 表示开着随机，`toolbox_theme_last` 存**本次开机摇到的日间皮肤 id**。⚠️`applyTheme` 每次都会把真实皮肤 id 写回 `toolbox_theme`，所以随机模式下每次 `applyTheme` 之后都要**把 `'random'` 补写回去**（`themeRandomApply` 干这事）——看着像多余的 `setItem`，删了随机开关一用就自己关。规则：**开机换一个日间皮肤；夜间钉死**蓝金**(`THEME_RANDOM_NIGHT_ID = 'warm'`，用户先说蓝橙、当天改口蓝金)不参与随机；日夜来回切不重摇**（只有开机和手动点🎲才 `themeRandomRoll`），摇的时候排掉上一次那个、免得「随机」了却没变化。手动挑具体皮肤＝自动关随机（`applyTheme` 写入具体 id 顶掉占位串）。⚠️小窗**开着时也会变**：在窗里切日/夜，🎲那行右边小字要从「夜·蓝橙」变回日间皮肤名，所以列表渲染抽成了 `renderThemePickerList()` 给 `showThemePicker`/`themePickerToggleNight` 共用。⚠️**夜间那档的显示名走 `themeRandomNightName()`、别把皮肤名写死进文案**——改常量时最容易漏掉文案，结果小字写着一个皮肤、屏幕上是另一个（第一版写死「蓝橙」，改成蓝金时就漏过一次）。⚠️`updateStatusBarColor` 里有一段把 `'random'` 换算回真实皮肤的逻辑，别删——否则状态栏取不到色会回退成粘土蓝。**内核早就写好了、缺的只是入口**（两个主题列表都只渲染 7 个具体皮肤），所以这次几乎没动主题机制本身。
- **⚠️想让阅读正文里的强调字更醒目时，别去提亮 `--accent`**：它有 **73 处是当背景用的**（上面压 `#fff` 白字），提亮＝白字糊成一片。改 `--accent-read`——定义在 `body {}` 上、默认 `var(--accent)`，只被阅读正文那 4 处上色的字（对话 `.reading-quote` / 人名 `.reading-name` / 精句 `.reading-keysent` / 点评人名 `.reading-q-name`）和配套的虚线下划线吃到。⚠️**它必须定义在 `body` 上、不能写进 `:root`**：主题变量挂在 body 的 `.theme-xxx` 类上，`:root` 里写 `var(--accent)` 只会取到 `:root` 自己那份默认值，所有皮肤一起串色。目前只有 `紫粉·夜` 覆盖了它（`#d5b0ff`）。
- **紫粉·夜为什么单独提亮**（2026-08-08）：皮肤强调色一度被改成朱玫红 `#ff6b6b`，用户说「颜色太名不副实」——叫紫粉却一点紫粉没有；换回 `--accent` 兰紫 `#c08cff` ＋ `--accent-mid` 粉紫 `#ef8ed0`（两者亮度相当，按钮的 `accent→accent-mid` 渐变正好读成「紫到粉」，**别把 accent-mid 调成 accent 的深一档**，那样粉就没了）。但她接着反馈「阅读模式下不好看」：**紫在暗底上的视觉亮度天生比红/粉低**，当按钮底色正好、当字色混在白正文里就发灰发闷 → 才有了上面那条 `--accent-read`。

- **窗口化渲染（进会话防卡顿）**：长篇会话进入只渲染「上次阅读位置→末尾」窗口，早章上滑到顶自动补渲染。`chatRenderAllMessages(windowed)`（**只进会话那次传 true**）、`chatComputeRenderStart`（以 `reading_pos_<convId>.idx` 为锚、前留 `READING_RENDER_BUFFER=4`）、`chatLoadEarlier`（补渲染并用高度差修 scrollTop）。**阅读定位靠「第几条消息+第几段」锚点（`.reading-merged p[data-p]`），不靠像素，所以少渲早章不影响回原位。**
  - **秒出 + 后台补（2026-06-20 修）**：先同步画 `READING_RENDER_FIRST=18` 条让界面秒出，其余 `setTimeout` 每批 `READING_RENDER_FWD_BATCH=8` 条后台补、接末尾（不移动已定位）。`_chatRenderToken` 代次令牌作废在途补渲染。用 `setTimeout` 不用 `rAF`（页面隐藏时 rAF 暂停）。
  - **双向窗口化 + 裁剪（2026-07-08 修，治「提前发十几章滑到最顶卡+烫」）**：早先只封窗口「起点以上」，起点以下一直渲染到全书末尾——于是把十几章(≈20万字)提前发出去、再滑到最顶从头读时整本书都堆进 DOM，滑动卡、手机烫。现在**起点以下也只先渲染 `READING_RENDER_FORWARD=12` 条**，底部挂 `chatMakeLaterSentinel`「↓ 载入后面章节」，滑到接近底部自动 `chatLoadLater` 补、对称于顶部的 `chatLoadEarlier`。`chatRenderEndIdx`＝已渲染的「末条+1」(==`chatMessages.length` 即到真末尾)。窗口超 `READING_RENDER_MAX=24` 条就从**远离视口那端裁掉**（`chatTrimTopIfNeeded` 带 scrollTop 高度差补偿 / `chatTrimBottomIfNeeded` 在视口下方无需补偿），实测全程 DOM 恒定 ≤~20 条、不随发章数增长。
    - **发新章/流式/生图接末尾前必须 `chatEnsureRenderedToEnd()`**（补齐窗口到真末尾+删底部哨兵），否则新节点接到哨兵后头、和未渲染的中间几条**串位**。已接：`chatSend`、`chatDoRequest` 收尾、`chatInsertGenImage`；这些追加后都要把 `chatRenderEndIdx = chatMessages.length` 同步、并 `chatTrimTopIfNeeded`。截断/删除(`chatSheetTruncate`/`chatSheetDelete`)按新长度校正 `chatRenderStartIdx/EndIdx`。

    - **⚠️阅读模式书签/划线必须按「章节号」匹配（2026-07-19 修「每章固定位置冒幻影标记」）**：书签(`reading_bookmarks`)/划线(`reading_highlights`)按 convId 存、原本只记 `msgIdx`+段号。共读会话单调增长 msgIdx 稳定没事；但**阅读模式(`chatReaderMode`)每次开章临时重建会话，同一 msgIdx 会对上不同章**——历史某 msgIdx 的标记就漏到每一章相同段号上。修法：保存时同时记 `chap: _readerChapOf(msgIdx)`（=该消息 `readerChapter`）；`_markMatchesMsg(mark,msgIdx,chap)` 在阅读模式按 chap 匹配、共读按 msgIdx。涉及 `readingMarkBookmarks`/`readingApplyHighlights`/`readingIsBookmarked`/`readingRefreshBookmarkUI` + 保存点(`rdHlCreate`/段落书签 toggle/`readingAddQuestionBookmark`) + 面板条目带 chap + 跳转(`readingJump*` 走 `_readerJumpTo`：没载入就 `readerOpenChapter` 再轮询滚到位)。旧数据无 chap → 阅读模式不显示/跳转给提示（它们本就错位，丢弃即可）。测试 `test_reader_marks.js`/`test_reader_jump2.js`。
    - **⚠️阅读模式读痕跨设备同步（2026-07-21 修「共读能同步、阅读不能」）**：根因是**存储键跨设备不稳**——共读会话 id `chat_<...>` 跨设备一致，阅读是 `reader_<本地bookId>` 而 `bookId='bk_'+时间戳+随机` **每台设备各生成**（导书/下载都会本地新 id，见 `bkSyncDownload`/`rbAddBook`），所以同一本书读痕对不上号。修法三层：① 新增 `readingMarksConvId()`——阅读模式(reader_ 前缀会话)把读痕键换成跨设备稳定的 `reader_<文件名|大小>`(=`readerBookKey`，与 `reader_qa` 同款)，8 处读痕存取点统一走它；`readerMigrateMarksKey`(进书时)+`readerMigrateAllMarksKeys`(开机 idbInit 后全量扫描)把旧键数据幂等搬到新键并重推。② **读痕面板「提问」在阅读模式直接从 `reader_qa` 生成**(`rdTraceReaderAskEntries`)——它与正文问答同源、已证实能跨设备同步(正文有问答=读痕就有)，彻底绕开易丢的 `reading_bookmarks`；按章#段聚单问/追问串、答案取 `reader_qa`、章名取书章节标题、跳转按章(msgIdx 可空)。共读/翻译仍走原书签路径。③ **`reading_bookmarks`/`reading_highlights` 云端合并由「整块按时间戳覆盖」改为「逐会话键取并集」**(`_mergeMarksBlobs`+`_readerMergeMarks`，签名去重、同源同 ts 不重复)——旧覆盖式一台设备一保存就把另一台读痕整块盖没(这是跨设备丢失的另一根因)；并集有新增则回推(cfSmartSync 里 `marksDirty`)，能自愈此前被覆盖的数据。**代价**：并集不传播删除(划线删除可能被另一台复活；但阅读模式提问删除由 `reader_qa` 每章 LWW 正常传播)。测试 `test_marks_key.js`/`test_sweep.js`/`test_reader_qatrace.js`。
    - **⚠️阅读模式正文问答换设备要「重灌」（2026-07-22 修「读痕有内容但正文看不到问答」）**：`reader_qa` 按稳定键跨设备同步、是权威；但正文靠 `readerChapterPair` 在**开章那刻**从 `reader_qa` 现拼成 `assistant.content` 快照，`chatSaveCurrentConv` 存的是那份快照。换设备时设备B常在「问答还没同步来」的空窗期就开过书、存了**空版正文快照**，之后 reader_qa 才同步到（→读痕面板直接读 reader_qa 有内容，正文快照仍空）；而「继续阅读」走 `chatLoadConv` 每次都从空快照恢复、不回灌。修法：新增 `readerHydrateLoadedQA()`，`chatLoadConv` 命中 `reader_` 会话时（**渲染前**、`if(chatReaderMode)` 块内）用 reader_qa 把每章 `readerChapter!=null` 消息的 content 重拼，不打乱滚动锚点。开章路径本走 readerChapterPair 现拼、不受影响。**遗留边角**：正在读某章时才同步进来的新问答，得重开该章才显示（没做实时重渲染，避免打断阅读位置）。测试 `test_reader_hydrate.js`。
