# 共读提问与成本控制

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **⚠️共读提问/点评是可并发的，别退回全局单锁（2026-07-30 改）**：用户报「阅读时如果有背景知识在生成、或共读提问在生成，就没法对其他段落双击，总要等它们生成完；翻译模式下就可以同时翻译不同段落」。**两个根因，只修一个照样会撞上另一个**：① 一把全局锁 `readingCommenting`，`readingOnParaClick` 第一行就把双击挡回去；② 正在生成的小气泡是**手工 `insertBefore` 进 DOM 的、不属于渲染数据**，标背景那种「边标边整条重渲」的循环一过，气泡连同刚弹出来的提问条一起被抹掉——**这才是「标背景时双击没用」的真因，跟锁无关**。改法**照抄翻译模式现成的 `translatePending`**：`readingPending` 每笔一条记录、各自带 AbortController，占位/流式气泡由 `readingModeRenderMerged`（新增可选第 3 参 `msgIdx`）**从数据里画出来**，重渲多少次都还在；`readingPendingHtml` 一套骨架给占位态和流式态共用（翻译那边是分两处写的，别照抄那半）。
  - **`readingCommenting` 保留成派生量**（`readingSyncBusy` 维护），`_waitIfStreaming` 那类旧调用方一字不用改——**别删这个变量**。
  - **⚠️记录存 `msg` 对象而不是 `msgIdx`**：往上滑补上一章会让所有下标整体挪位（同 `readerMarkBg` 那个「34 章的背景插进 33 章」的坑），渲染/收尾时一律现查 `chatMessages.indexOf(msg)`。`readingAskOne` 收尾原来直接用进函数时的 `msgIdx`，属同一类隐患，一并改掉了。
  - **提问条要在重渲后接回来**（`_rdActbarState` + `readingRestoreActbar`），连同打了一半的字；**接回来时不抢焦点**（`opts.noFocus`）——用户多半正在读，顶起键盘很烦。
  - **流式跟随改成「只在气泡已露在视口里才 `scrollIntoView('nearest')`」**：并发之后你可能问了 P10 又滑到 P30 去问，P10 出字时把你拽回去是最烦人的；`'nearest'` 对完全可见的元素是空操作，所以「正在看的那条边长边跟」照旧成立。
  - 同一段重复发由 `readingIsPending` 挡（**要等 guide 把 pNum 改写成小标题段号之后才判得准**），不白扣费；「停止」按钮只掐自己那一笔。
  - 测试 `tests/concurrent.test.js`（31 条）。⚠️**写这类测试要在每组开头清 `readingPending`**（`while (readingPending.length) readingRemovePending(readingPending[0].id)`）——上一组故意挂着不放行的请求会跨组累加，第一版就是这么假红的。

- **提问「带多少材料」三档小方块（2026-07-28 加）**：用户要自己决定每次带不带记忆表和摘要（「这个切换也走极简风」），选的形态是**一个小圆点、点一下换一档**，取代了原来那个「带前文问答」勾选框。⚠️**档位梯子的顺序不能改**：`0 只带原文 → 1 ＋记忆表和摘要 → 2 ＋本章前文问答`。这么排是因为**现状恰好落在 1 和 2 上**（表格摘要一直是 always on、前文问答才是可选的），换成「◐＝带问答、●＝全带」那套，「带表格但不带问答」这个现行默认就无处安放、会在用户没要求的情况下改掉她的行为和花费。存两个键：`reading_ask_lv`(普通提问，默认 1) / `reading_ask_lv_bg`(背景追问，默认 0)——**默认不同，合成一个键会打架**；老键 `reading_ask_ctx='1'` 迁移成 2。读取 `readingAskLv(isBg)`，`_lv>=1` 放行记忆表/摘要（**三条 `else if` 分支都要挡**，第三条 `readerEnsureSummaries` 会现场调 API），`_lv>=2` 放行 `priorQaBlock`。控件**用 CSS 画不用 ○◐● 字符**——半黑圆在部分安卓字体里会掉字，而它全靠形状表意。`readingAskCtxBoxHtml/readingBindCtxBox` 保留成薄壳转发，避免散着改漏调用点。测试 `tests/askcost.test.js` E 组（11 条）。

- **双击背景块＝背景追问模式（2026-07-28 加）**：用户报「双击的明明是背景知识，AI 却带入正文人物的动机跟我交流」。**根因**：`readingOnCommentClick(bqEl)` 只从块上取 `data-cp`（段号），**把「你双击的是哪一块」直接扔了**——于是双击背景块和双击正文段落发出去的东西**一模一样**：共读点评人设 ＋「结合该段原文认真回答」＋记忆表/摘要，三样都在往剧情上拽，那条背景讲解只是「你之前对 [P19] 写下的评论」里的一个小圆点。跑偏是必然，不是偶发。**修法**：渲染时给背景块打 `data-bg="1"`（`_cmtRaw` 去掉「汐：」后以 `BG_Q_PREFIX` 开头），`readingOnCommentClick` 把 `data-ci` 当 `opts.bgCi` 传下去 → `readingOpenAskBar`（按钮固定「追问」、不接长按第三态、空态只聚焦输入框）→ `readingAskOne` 的背景分支：人设换 `BG_NOVEL_PERSONA`/`SOCIAL_MODE_PERSONA` + 新的 `BG_FOLLOWUP_INSTRUCTION`，材料只有**那一条背景讲解 + 前后各三段原文**，**不带记忆表/摘要/同段其它问答**，记账单列成「背景追问」。实测 3558 → 1521 字（用户真机上普通提问是一万多）。⚠️**三条 `else if` 摘要分支都要挡**——第三条 `readerEnsureSummaries` 会**现场调 API 生成摘要**，漏挡等于白烧一笔它根本不需要的钱。⚠️**不是禁止聊剧情**：用户原话「不是说不可以聊正文」，定的是**背景优先、她问到剧情才聊**；写成硬禁令会从一个毛病换成另一个毛病（她顺口问「那他是不是在装傻」被拦回去）。⚠️**双击普通问答块那条路一字未改**，记忆表/摘要照带——「想认真聊剧情就双击正文」是这个设计的另一半，别顺手也给砍了。测试 `tests/askcost.test.js` D 组（15 条）。

- **共读提问的输入分块量表（2026-07-28 加）**：用户问「共读提问一次上万 token、主要是输入，怎么优化」。总数看得见、构成看不见，砍哪一块全靠猜——而且**记忆表格和前文问答有多大只有用户手机上的数据知道**，服务器这边测不出来。所以定的是「先量再砍」：`readingAskOne` 在发请求时算一份 `_parts`（各块**字数**，不是 token——token 只有整笔的真实值、拆不到块，比例够用来做决定），经 `chatStreamChat(opts.parts)` → `apiLogRecord(..., parts)` 落进明细日志，用量面板里那一条**点开就是一排条形图**（`_apiPartsHtml` 按字数倒序、`apiLogToggleParts` 就地切显示——⚠️不能整块重渲，`apiLogRenderBody` 会把展开状态冲掉）。**只记共读提问**（用户明确说社科导读没必要）。⚠️**记忆表和摘要必须分开记**（2026-07-28 拆）——最初合成一块「记忆表+摘要」，用户在真机上量出**这一块 6700 字 / 总共一万多**，正要决定砍哪个，而量表恰好在最该分辨的地方糊住了，等于没量。**教训：分块宁可拆细别合并**，合并的代价是整轮白量。**服务器实测靠不住**：造的假书里原文占 81~88%，而用户真实数据里原文只占三成——记忆表和摘要是全书累积的，服务器这边没有那份数据。⚠️**新增输入块必须同步加进 `_parts`**——`tests/askcost.test.js` 有一条断言核对「分块合计≈真正发出去的字数（误差<5%）」，漏记一块就会红，因为漏记会让用户按错误的比例去砍、白折腾一轮还以为是自己判断错了。**下一步待定**：`CTX_CHAR_BUDGET=8000`（`readingAskOne` 里）是最大的一块，等用户看过真实占比再决定砍到多少。**已排除的方向**：① 记忆表和摘要是绑在一起发的（同一条 system 消息、一个 if/else 链），曾想把 ◐ 拆成两档分别控制——用户 2026-07-28 明确说「**5 段前情我可以接受**」，**别再提砍 `CHAT_SUMMARY_MAX_SEGS` 或拆档**；② 社科导读不记分块（用户说没必要）。

- **⚠️阅读摘要截断上限 40000（别调回 16000）**：`readerSummarizeChapterOnce` 里 `body.slice(0, 40000)`。原值 16000 对网文（三五千字/章）绰绰有余，但社科书一章 34000~39000 字，**一半以上正文被静默切掉、摘要只概括了前半章**（2026-07-27 修）。短章节从不触及此分支。
