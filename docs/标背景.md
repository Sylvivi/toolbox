# 阅读模式「标背景」

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **阅读模式「标背景」（2026-07-27 加）**：解决「读非虚构缺的不是生词、是背景」——字都认识，但不知道那个年代/制度/学派是怎么回事，而且**往往不知道自己缺**，所以做成系统主动标、不是等她想起来问。入口在**目录**：阅读分支每行统一一个「⋯」（跟书架的书一致），菜单＝`🏛 标背景 / ✂️ 手动分章 / 🗑️ 清掉本章背景`；**✂️ 从行上收进了菜单**（长章原本比别人多一个图标，收进去反而齐整），meta 行显示 `· 🏛 已标 N 条`，并**去掉了行尾的「阅读 ›」**（用户嫌多余）。**共读分支的目录一字未动**（仍是 ✂️＋＋，无 ⋯）。
  - **两遍法（别改回一遍）**：一遍到底＝把整章丢给模型让它自己看着办，那正是共读「散漫点评」的形状——用户原话「散漫地点评，模型注意力一般」，前几段挑得细、后面就敷衍。所以 ① `_rdBgScan` 用**便宜的压缩模型**只列清单（`P段号|背景点名`，输出短＝注意力不被拉长），超长章按 `BG_SCAN_CHUNK=20000` 切段分别扫；② `_rdBgExplain` 用**主模型**逐条讲，每次只喂这一个点 + 前后一小圈上下文。
  - **⚠️模型必须在 `readerOpenChapter` 之前定死**：它调 `chatResetConvState()` 会把 `chatSelectedModel`/`chatSelectedKeyStr` **清空**，之后要等 `chatLoadModelsForCurrentKey` 异步恢复。`readerMarkBg` 开章前就算好 `explainM` 传进 `_rdBgExplain`——现读全局的话，从目录标一个没打开的章节会拿着**空模型名**发请求（实测踩到过）。
  - **零新增存储键**：一个背景块＝一条 q 以 `BG_Q_PREFIX='背景：'` 开头的 `reader_qa` 问答。云同步、换设备重灌、长按删除/重新回答、读痕面板**全部白拿**。跨章去重靠 `readerBgDoneTerms(fileKey)` 扫全书已讲过的词、塞进第一遍的「已经讲过、请跳过」。**⚠️比对必须走 `_rdBgKey(t)` 归一化**（2026-07-27 加）：原来是一模一样的字符串比对，模型这一章写「共济会」、下一章写「共济会（Freemasonry）」就成了两个词，用户被讲第二遍还扣一次费。归一化抹掉括号注解/书名号引号/空格中点连字符/英文大小写/全角字母数字，**只用于比对，显示仍用模型给的原样**。⚠️故意**不做包含关系**（「独立战争」⊂「美国独立战争」）——那会把「宪法」和「美国宪法」这种真该分开讲的也无声吞掉。注意：喂给模型的「请跳过」名单仍是原词（给人和模型看的），硬过滤在客户端。
  - **⚠️车轱辘话：同一段被拆成三四条讲同一件事**（2026-07-28 修，用户实测《大唐辟珠记》第 44 章）。第 19 段同时出了「高门女子悬丝诊脉与帷幔隔诊」「帷幔隔诊」「丝帕覆腕诊脉是高门女眷就医礼制」「悬丝诊脉与帷幔隔诊礼制」四条——**四次扣费、四个块堆在同一段下面**。`_rdBgKey` 只抓「同一个词的不同写法」，抓不住「同一件事的不同说法」。三道闸：① 提示词要求背景点名称是**短名词（2～8 字、词典词条那样）**，明令禁止「…是…」「…指…」这种解释性尾巴，并写死「同一段最多只列 1 条」；② `_rdBgNear(a,b)` 近义判定＝包含关系 ∪ 字符重合率≥50%，两者都要求短的一方≥4 字；③ **每段额度按段落长度给**：`_rdBgCapOf(line)` ＝ `1 + floor(字数/200)`、封顶 `BG_MAX_PER_PARA=3`。⚠️**别写死 1**（用户 2026-07-28 提醒）——小说段落短、一段一件事，1 条正好；自传/社会学的段落动不动三五百字，里面真有好几件互不相干的事，写死 1 条就是漏。**故意不按书籍类型分岔**：段落长度本身就是更准的信号（社科书的段落天然就长），而小说里偶尔一段长描写多给一两条也不冤。**⚠️`_rdBgNear` 只许在同一段之内用，别顺手推广到全章**——跨段的「宪法」/「美国宪法」、「独立战争」/「美国独立战争」是真该分开讲的（C2 组测试守着这条线，推广过去会当场变红）。重标同一章时靠 `_rdBgScan` 的第 7 个参数 `donePara`（`readerBgOfChap` 出来的 `{p,term}`）把段号带进来，否则「这段已经有一条了」无从判断，再标一轮又叠一层。
    - **⚠️⚠️这三道闸里，第①和第③收过头了，2026-08-03 放宽（别再往回改）**：用户读一篇讲司马迁的文章时报「**一段里其实会出现不少要解释的背景点，但模型通常只解释一个，这就导致我还需要二次提问**」，并且**自己指到了病根**——「可能跟我之前担心一段会有重复的背景点、设了限制有关」。她是对的：**要治的从来是「同一件事说四遍」，不是「一段里事情多」**。真正对症的是闸①的「名字必须是短名词、不许带解释性尾巴」和闸② `_rdBgNear`（它们管"重不重复"）；而「同一段最多 1 条」管的是"多不多"，**拿数量去治重复，代价就是把真有好几件事的密集段落砍掉**——历史类文章一段里「太史令」「腐刑」「李陵之祸」「天汉三年」是四件互不相干的事，按老公式 150 字只准 1 条，必然漏三件，她只能一条条二次提问。
    - 具体改动：提示词里「**同一段一般只列 1 条**」→「同一件事只列一条 + **一段里有几件互不相干的事就列几条，别为了少列而漏掉**」（并举了官职/刑罚/事件/年号那个例子）；`BG_PARA_CHARS_PER_PICK` 200→**120**、`BG_MAX_PER_PARA` 3→**4**。闸②近义去重原样不动，它才是防重复的那道。回归 `tests/bg.test.js` N 组（新增「密集段四条都留得住」，用的就是司马迁那段的形状）。
  - **边标边插必须包 `_rdKeepScroll(msgIdx, fn)`**：插入点在视口上方会把正在读的那一行顶跑（实测不锚定会从 P22 窜到 P21）。它记下视口顶部那段的位移、重渲后用差值补 `scrollTop`。**别直接 `readingRerenderMsg(mi, focusP)`**——带 focusP 会 scrollIntoView 把用户拽走。
  - **⚠️再点＝「接着标」，不是重标**（2026-07-27 当天改）：初版是「本章标过 N 条，清掉重标吗？」——用户实测跑到第 4 条就失败，于是只能在「留着残缺的四条」和「全推倒重来」之间二选一。现在不清空，已讲过的词由 `readerBgDoneTerms` 收进第一遍的「请跳过」名单，天然接得上；真想重来走菜单里的 `🗑️ 清掉本章背景`。
  - **⚠️单条失败不许拖垮整轮**（同上）：`_rdBgExplain` 每条重试一次（间隔 1.5s），仍失败就 `failed++` 跳过、接着下一条；只有连清单都没拿到才算整轮失败。中转站偶发 429/超时很常见，为此把后面十几条全废掉太亏。收尾 toast 会报「已标 X 条，Y 条没成功：<错误>（再点一次「接着标」会补上）」。已插进去的每一条都是**即时落盘**的，任何失败都不会丢。
  - **⚠️开章会把模型选择清空——已在 `readerOpenChapter` 里修（2026-07-27）**：`chatResetConvState()` 清 `chatSelectedModel`/`chatSelectedKeyStr`，而 `readerOpenChapter` 不像 `chatLoadConv` 那样从 conv 恢复。后果是**从目录点一章之后，导读/共读提问/标背景全弹「请先选择模型」**；更坑的是它随后 `chatSaveCurrentConv` 把 `model:''` 写回这本书的会话，下次载入照样空——**不是一次性的，会一直烂着**（用户报「明明选好了模型，每次点接着标都让我重选」）。修法：重置前存下旧值，重置后按 `旧值 → readerFindConv(bookId).model → chat_last_model_<provId>` 还原，并同步 `chatModelInput`/`chatModelLabel`/发送键。
  - **⚠️`chatStreamChat` 没有任何超时**：中转站卡住不返回时 `await reader.read()` 永远挂着。标背景是十几条的循环，一条挂死就整轮不动、还把 `readerBgRunning` 焊死在 true（用户报「很久都不响应」）。所以走 `_rdBgTimed(opts, ms, who)`——每条自带超时闹钟（找点 120s / 讲解 90s），**超时抛普通 Error（可重试/可跳过），用户按停止才抛 AbortError（整轮结束）**，两者必须区分开。运行中再点菜单会 `confirm('要停下吗')` 而不是闷不吭声地挡回去。
  - **⚠️超时提示必须点名是「哪个模型」没回（2026-07-27 修）**：两遍走的是**两个不同模型**（第一遍摘要模型、第二遍主模型），旧文案只说「中转站没回」，用户直奔聊天那个中转站去查、那边好好的，于是以为不是模型的事（原话「说是中转站问题，可是中转站没问题呀」）。`_rdMdlName(m)` → `模型名@域名`，由调用方传给 `_rdBgTimed` 的第 3 参 `who`。
  - **⚠️第一遍 `max_tokens` 必须给足（4000，别调回 800）**：`chatStreamChat` **只收 `delta.content`，思考型模型的推理过程不算在内**。800 对不思考的模型绰绰有余（清单就二十来行），但思考模型光"想"就把额度用光、正文一个字都吐不出来 → `out=''` → 0 条 → 每次都报「这一章没有新的背景要补」，而两万字输入和推理 token 照样计费。用户实测连点三轮、烧了额度、一条讲解都没有。按实际生成量计费，抬上限对不思考的模型几乎不增加成本。
  - **⚠️第二遍 `_rdBgExplain` 是同一个坑的第二处（2026-07-27 修，当天先只修了第一遍、漏了这里）**：`max_tokens` 原为 **700**——讲解本身才 120 字（约 200 token），剩 500 给思考**正好卡在边界上**，于是「第 1 条插进去了，后面全没了」。空回复走 `if (!txt) { failed++; continue; }`，**请求发了、钱扣了（还白重试一遍）、却什么都没插**，收尾提示只有「N 条没成功：」后面空空如也。已改 4000，并让**空回复抛描述性错误**而不是返回空串——否则 `lastErr` 是空的，用户完全看不出为什么。**改这类上限时两遍必须一起改。**
  - **⚠️⚠️别把 msgIdx 揣在兜里跨过 await（2026-07-28 修，这是「9 条只成 1 条」的真凶）**：标背景一轮要发十几个请求、几十秒，而用户还在读——只要往上滑到章首，`readerPrependPrevChapter()` 就把上一章插到数组最前，**所有消息下标整体 +2**（那函数自己也要把已渲染节点 `data-idx` 和书签的 msgIdx 一起 +2，可见早有先例）。于是循环里捕获的 `msgIdx` 指到上一章头上：用户实测「三十四章的背景插进了三十三章」。**同一个根因也解释了之前那次「生成 9 条、读痕只剩 1 条」**——后 8 条没丢，是写进上一章去了；踩不踩到全看那一轮有没有往上滑，所以时好时坏、换不换模型都可能复现（我一度误判成模型问题）。修法：**捕获消息对象 `msgObj`**（对象引用不会因插队失效），内容写 `msgObj.content`；DOM/落盘要的下标每条现查 `chatMessages.indexOf(msgObj)`，查不到＝这一章被卸载了，当场停下并提示重开再「接着标」，绝不把内容写到别处。⚠️`readingAskOne` 早就是持对象的写法，改这类循环时照它抄。回归测试用「讲完第 1 条就插一章进数组」来复现（把修法改回去会立刻红 4 条）。
  - **进度条点开＝这一轮的背景点清单（2026-07-28 加）**：用户原话「不然我总要等到全部生成完才知道有哪些」——清单第一遍就扫出来了，没理由捂到最后。`_rdBgPicksSet(picks)` 在扫描一返回就填，`_rdBgPicksMark(k,st)` 在循环里推进（`wait 待讲 / run ⏳ / ok ✓ / fail ✗`）。点 `#rdBgBar` 本体展开 `#rdBgList`（另起一个 fixed 元素、钉在条子正下方，**不做成子元素**——条子是 `width:fit-content` 的胶囊，塞进去会把胶囊撑变形）。⚠️「停止」键要 `stopPropagation`，否则想停却把清单展开了；⚠️`_rdBgListPlace()` 要挂进 `_rdBgBarPlace()`，条子随滚动移位时清单得跟着走；⚠️`_rdBgBarHide` 要连清单一起收、并清空 `_rdBgPicks`。
  - **⚠️间歇性失败：退避重试 + 条间限速 + 跑的时候别推云（2026-07-28 加）**：用户实测《大唐辟珠记》9 条只成第 1 条，后来**没换模型再跑一遍却全成了**——所以不是某个模型固定坏，是**间歇性**的。「第 1 条成、后面连挂」正是"连着猛发"的形状：这个循环原本背靠背发请求，一秒能打出去七八个，很容易撞中转站频率限制。三处一起改：① 重试 1 次固定等 1.5s → **3 次退避 0/2s/6s**，错误里带 429/rate/too many/频率 再至少等 8s；② **每条之间 sleep 500ms**（9 条只多 4 秒）；③ `_readingNamesWrite` 的推云防抖遇到 `readerBgRunning` **一直往后顺延**——那一轮每插一条就并一次名单，3 秒防抖必然在中途触发，等于在十几个模型请求当间插一次整包上传、跟它们抢手机的网。⚠️这三条都是**减少诱因**，不是确诊；真正的诊断靠 sticky 失败提示里的原因文字。
  - **⚠️失败提示必须 sticky + 说清空回复的两种成因（2026-07-28 加）**：收尾那句 `showToast(...)` 原来**没传第 2 参**，2 秒就自己消失——而它恰恰是「钱花了却什么都没拿到」时唯一的解释。用户实测《大唐辟珠记》9 条只成 1 条、其余全白扣费，回头只记得"扣费了、只插进去一条"，完全不知道败在哪。现在失败一律 sticky（成功的照旧自动消失）。同时 `chatStreamChat` 增加 `_lastThinkLen`（**只数不收** `delta.reasoning_content/reasoning/thinking` 的长度，别拼进 `full`），`_rdBgExplain` 据此把空回复分成两种：**「只吐了思考过程（约 N 字）」→ 换个不思考的讲解模型**；**「一个字都没回」→ 中转站/模型本身的问题**。两者处置完全不同，含糊一句话会害用户白点好几轮。
  - **⚠️空清单必须分四种报（2026-07-27 加）**：`_rdBgScan` 返回 **`{picks, replies, matched}`**（`replies`=各段原始回复，`matched`=正则认出的行数，含随后被滤掉的）。调用方据此分开：`matched>0`→「这一章的背景点都已经讲过了」（模型照做了，只是词都被 `doneTerms` 滤掉——**初版漏了这条，会误报成「没按格式回」冤枉模型**，实测踩到）；`replies` 全空→「模型一个字都没回（多半是 max_tokens 被思考过程吃光了）」；`^无$`→「这一章没有新的背景要补」；其余→「模型没按格式回，认不出清单：<前 40 字>」。**混为一谈的代价是真金白银**：用户以为「这章确实没背景」，又点两轮想让它接着标，每轮都把整章完整喂出去一遍。
  - **⚠️渲染会静默丢弃段号越界的块**：`readingModeRenderMerged` 的 `for (j < pHtml.length)` 只输出 1…段落数 之内的 `commentMap[pNum]`，超出的**既不报错也不进章末兜底（那个只收 p≤0），凭空消失**；而 `readerPersistQA` 存的时候不检查范围。所以「reader_qa 里有、正文里没有、重开还是没有」是可能的。排查「生成了但不插入」时，先用**读痕面板**（直接读 reader_qa）对一下条数，就能区分「没存进去」和「存了没渲染」。
  - **清单解析要容错**：只认严格的 `P7|共济会` 时，模型稍加列表符号/编号/加粗/中文冒号就整轮解析不出东西。段号越界、重复词仍照旧丢弃。
    - **⚠️2026-08-03 又放宽了一大截（用户报「提示模型没按格式回，试了两次都失败」）**：**第一遍走的是摘要模型**（`chatResolveCompressModel`），那多半是个便宜的小模型，而小模型最不擅长的就是死守格式。老正则要求**必须有 P 前缀 + 必须是 `|`/`：` 分隔**，于是这些只差一点点的写法一条都不认：`7|共济会`（吞掉 P）／`第7段|共济会`／`[P7] 共济会`／`P7 共济会`（空格当分隔）／`P7-共济会`／markdown 表格 `| P7 | 共济会 |`。**整轮 0 条，而整章两万字已经喂出去、钱照扣**。现独立成 `_rdBgParseLine(ln)`，上面全部认得出。
    - **⚠️宽是有边界的，两道闸**：① 段号前面既没 `P` 也没「第」时，**必须**有明确分隔符（`|｜:：、`）——否则正文里「1958 年大跃进那阵子」会被读成 P1958；② 用空格/短横线当分隔时，名字要 **≤20 字且不带句读**——否则「P7 这一段讲的是共济会，它……」整句会被当成背景点名称。
