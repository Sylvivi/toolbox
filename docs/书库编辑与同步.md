# 书库编辑与跨设备同步

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **正文「改错字」（2026-07-28 加）**：用户原话「我现在上传的书籍，我希望能够编辑……我需要改里面的一些错字，和添加一些作者新出的番外」。此前唯一办法是删书重传，读痕/摘要/背景全部陪葬。**入口＝选中那几个字 → 底部划线小条上的「✏️ 改」**（`rdHlShowSelBar`）——改错字的第一步本来就是选中错字，手势天生对上，零新增手势零新增图标。⚠️**别改成「长按段落」**：手机上长按正文＝系统选词，而选词正是划线的入口（`selectionchange` → `rdHlShowSelBar`），两者会正面打架。
  - **⚠️三条铁律**（`tests/edit.test.js` 71 条全钉死了，改这块必跑）：
    ① **身份证 `fileName`/`fileSize` 一个字节都不许动**。读痕/划线/问答/背景/名单/书籍类型/文件夹/阅读进度/云同步全按 `fileKey` 认书，而它是**导书那天记下的标签、不是拿正文现算的哈希**（`rbBookFileKey` 就读那两个字段），所以只要不碰它，编辑正文对上面每一样都是透明的。照抄「改书名」的先例。旁证：书架界面根本不显示文件大小（本地书显示阅读进度、远程占位显示章数、字数现算），冻住一个跟真实内容对不上的数字**无处露馅**。
    ② **段落数量永远不变**。段号＝正文里第几个非空行（`readingModeRenderMerged` / `readingModeAddParaNums` / `_rdEditFindLine` 三处必须同一个数法）。所以编辑框**禁止换行**（回车＝保存、粘进来的换行转空格、`rdEditApply` 里还有最后一道闸），且不许把整段清空。一拆一删，这一章后面所有读痕/背景集体错位，跟「34 章的背景插进 33 章」同类，而且更难发现。
    ③ **四份一起改**：眼前 DOM／会话消息（`chatMessages`）／书架那本书（`book.chapters`）／云端（`bkSyncPush`）。只改会话＝书还是错的（重读、换设备照旧错）；只改书＝眼前不变。
  - **⚠️正文不在你点的那条消息里**：共读/阅读的正文渲染走 `readingModeGetOriginalText(msgIdx)`——从当前消息**往前找最近的 user 消息**，正文在那儿；点的那条（`.chat-msg.ai`）装的是点评/问答/背景块。而划线/书签/问答记的 msgIdx 都是 AI 那条。所以改正文前必须先 `_rdEditOrigMsgIdx(msgIdx)` 挪一格。**第一版直接改了 AI 那条 → 每次都报「找不到这一段」**，回归测试 C 组当场逮到。
  - **认章号**：阅读模式看 `msg.readerChapter`（100% 准）；**共读模式会话只记了书、没记章号**，靠 `_rdEditBookTarget` 用整章内容精确比对反查（`_rdEditNormText` 剥 `[Pn]`＋逐行 trim＋丢空行）。**在用户真实书库上实测：359 本 / 21624 章，只有 0.51% 的章节存在"另一章一字不差"**（且基本是切章切坏的碎片 `<br>`/`……`）。退路是按章标题唯一匹配——**17% 的书有重名章标题**，所以那条路写死了「重名就放弃」，宁可不改也不能改错章。都认不出时**只改会话并 sticky 提示「书没改」**，绝不瞎猜。
  - **⚠️共读消息带 `[Pn] ` 前缀，写回时必须还回去**（`_rdEditFindLine` 记下 `prefix`）——丢了整章段号解析全乱。
  - **划线跟着挪**（`_rdEditShiftHl`）：改动左边不动、右边平移 delta、压在改动上的撑开包住新字；`text`/`preview` 一并重算，否则读痕面板一直显示改之前的错字。**书签是段级的，不受段内改动影响。**
  - **后悔药**：`reading_book_edits = {fileKey:[{id,chap,title,p,start,before,after,ts}]}`，每本封顶 200，书架 ⋯「📝 改动记录」逐条 ↩️ 还原。⚠️**本地存、不进云同步**——正文本身已跟着书同步了，这张表只是操作痕迹；挂进 manifest 就得处理多设备并集（整块覆盖会把另一台的记录盖没，见下面同步心法），为一个后悔药付这个复杂度不值。还原前会核对「改后的字还在不在」，被二次改过就拒绝并说明。**书没改成（对不上章）就不记录**——记录挂在书上，无从还原。
  - **⚠️已知隐患（等第三块做完才消）**：跨设备自动更新**还没做**，所以别的设备会一直停在旧正文；而书架配置里那个手动「全上传」（`bkSyncPushAll`）会把该设备的旧正文推上云、冲掉改好的字。全局扫过：**没有任何自动/开机/定时的整书上传**（只有导新书、改字/还原、和这个手动按钮），所以不会自己倒灌，但那个按钮在旧设备上按下去就是事故。
  - 用户 2026-07-28 真机验过：「改了，没啥问题」。

- **追加章节 / 番外（2026-07-28 加）**：用户「添加一些作者新出的番外」。入口＝书架 ⋯ →「➕ 追加章节」→ 选 txt → 自动切章 → **预览确认**（列出每章标题、字数、接上去之后是第几章）→「接到最后」。`rbAppendStart`/`rbOnAppendPick`/`rbAppendSplit`/`rbAppendPreview`/`rbAppendConfirm`/`rbAppendChapters`，另起一个 `#rbAppendInput` 文件框（跟「添加书」分开，免得走串把番外导成新书）。
  - **⚠️只做「接到全书最后」，刻意不做「整本换新版」**（用户自己选的）：读痕/划线/问答/背景全按「第几章·第几段」钉位，接在最后＝前面每一章序号一动不动＝零风险；整本换新版要重新切章，章数或段数一旦对不上，前面所有标记**静默**集体错位，错了还不报错。
  - **⚠️`rbDedupChapters`/`rbFixChapterTitles` 只在「新来的这几章」内部跑**，跑完再 concat。前者会合并相邻同标题的章、后者会跨章挪副标题——放到整本上跑，万一动了已有章节边界就是上面那类静默错位。测试 C 组专门拿「新章跟已有末章同名」来守这条。
  - **⚠️`rawText` 必须一起接**：目录里的「重新拆分」(`rbReSplit`) 是拿 `rawText` 重切整本的，不接的话哪天点一下番外就没了。测试 B 组守这条。
  - **⚠️`fileName`/`fileSize` 一个字节不动**（同改错字的铁律①），`rbAppendChapters` 里还显式断言了一次。
  - **默认按这本书原来的切法切**（`b.preset`），预览里可以当场换切法就地重画。

- **跨设备自动更新（2026-07-28 加）**：改完错字/加完番外，别的设备原本不会跟着变——书是「本地为主、服务器当镜像」，`bkSyncInjectManifest` 里一句 `if (localKeys[fk]) return;` 就把已有正本的书整个跳过、压根没比时间。而服务器 manifest **早就带着 `ts`**（books.py 的 /manifest 就返回），牌是现成的。现在：本地书记 `_ts`（`bkSyncPush` 推成功时盖、`bkSyncDownload` 下载时盖），`bkSyncCheckUpdates(items)` 拉清单时比，服务器新就 `bkSyncRefreshOne` 重下正文并弹「《X》已更新（N → M 章）」。
  - **⚠️首次见面不下载、只盖时间戳**：老书本来没有 `_ts`，当成 0 的话一开书架就把几百本全重下一遍。所以第一次见到某本书认作"已同步"，**只有此后的改动才触发更新**。测试 F 组守这条。
  - **⚠️但「章数对不上」是例外，必须下（2026-07-28 补）**：用户问「改了字后怎么在别的地方同步呢」时发现的死角——她别的设备都还没"见过"任何书，第一次开书架只会盖时间戳，于是**服务器上刚批量修好的 90 本书永远同步不过去**，只能一本本手动删了重下。现在首次见面时先比 `m.nchap` vs `b.chapters.length`，不一样就下。`nchap` 是 manifest 现成字段、比对不花钱。⚠️**只认章数、不拿字数猜**：改错字不动章数，那种情况本来就该等下一次真更新，不值得为它把整个书库重下一遍。⚠️章数不对时**不能提前盖 `_ts`**（盖了就再也不会下了）——测试 F5 钉住。
  - **⚠️批量更新只报一个总数**：修完一批书可能几十本，一本一条 toast 会把屏幕刷爆。超过 3 本就 `quiet` 模式闷声下、末尾报「已更新 N 本书」；但**正在读的那本仍单独提示**（她眼前那一章得重开才看得到新内容）。测试 I3/I4 守这条。
  - **⚠️只换 `chapters`/`rawText`，保住本地 `id`**：`reading_conv_book`（哪个会话在读哪本书）、`rbActiveBookId`、阅读会话 id 全记着本地那个 `bk_<时间戳>_<随机>`，整个对象换掉会把这些关联全断。`fileName`/`fileSize` 同样不动。测试 H 组守这条。
  - **⚠️云端更旧时不下载**（别把新正文盖回旧的）；推成功才盖 `_ts`，否则会把自己刚推的当成"别人的更新"再下一遍。
  - 正在读这本书时提示「重开这一章看新内容」——正文快照是开章那刻拼的；同时作废 `_readingMergeCache`。
  - **⚠️遗留隐患**：书籍服务器配置里那个手动「全上传」(`bkSyncPushAll`) 在**还没更新过的**设备上按下去，仍会把旧正文推上云。自动更新只在打开书架（`bkSyncPullManifest`）时跑，所以"开一下书架再按"是安全的，但这个顺序没法强制。

- **重复导入拦截（2026-08-06 加）**：`rbAddBook` 开头用 `rbFindSameFile(fileName, fileSize)` 查一下书架里有没有同 fileKey 的**本地正本**，有就 `confirm` 问一句——「确定」＝ `rbOpenBook` 打开已有那本、不新增；「取消」＝仍然再存一份（用户明确要保留这个口子）。回归 `tests/dupbook.test.js`。
  - 起因：用户报「书架里有两本社会性动物」，补充的那句「两个会一起移动什么的」是关键线索——**两条记录的文件夹/书名/划线/小注全联动**，因为这些都按 fileKey 存，两条 fileKey 一样，数据层面本就是同一本书，只是 `rbBooks` 里排了两行。原来这里一句查重都没有。
  - **⚠️唯一不共享的是阅读进度**（`reading_pos_reader_<bookId>`，按书的内部 id 存，不是 fileKey）。所以清理重复条目时，删掉哪条就丢哪条的阅读位置；划线/小注/读痕/问答/文件夹全都不受影响。
  - **⚠️`_remote` 占位书不算重复**，必须跳过——否则「服务器上有、想导到本地」这条路会被自己堵死。测试 E 组守这条。
- **书籍/字体同步（自建服务器）**：正文/字体太大不进 CF，走自建 cc-books 服务器同步，前端函数前缀 `bkSync*`。书是「本地为主、服务器当镜像、按需下载」，占位书 `_remote:true` **不落盘 IndexedDB**；字体是「换设备启动自动全量拉回」。**服务端细节见私有 `SERVER-OPS.md`。**
  - **⚠️下载大书：进度 / 超时 / 失败原因（2026-07-30 加）**：用户报「这种大文件，我的手机同步半天都同步不下来」。最难受的不是慢，是**分不清在下、卡死了、还是早就失败了**——老 `bkSyncDownload` 就是 `fetch().then(r => r.json())`：没进度（等整包下完才动）、没超时（手机网络一卡永远挂着，同 `chatStreamChat` 那个坑）、失败原因全丢（`.catch(function(){ cb(false); })`，界面只写「请检查配置或网络」，而配置好着，**白让她去翻设置**）。现在流式读 `r.body.getReader()` + `onProg(已下,总共)` + `BK_DL_STALL_MS=60000` 无新字节自己掐断 + `cb(false, 原因)`，返回 `AbortController` 供「停止」。⚠️**三种失败必须分开说**：主动停 / 网络没响应 / 服务器报错——含糊一句会让她顺着错的方向反复试（同收藏模型那次「A 坏了却报 B」的账）。⚠️**判据是「多久没动」不是「跑了多久」**：慢但在动的网络不该被掐。⚠️**总量只能读 `X-Raw-Length`，不能读 `Content-Length`**：Caddy 给这条响应开了 `encode zstd gzip`，`Content-Length` 是**压缩后**的大小（边压边发时干脆没这个头、走 chunked），而 `response.body` 流里读到的是**解压后**的字节，两个数对不上、进度条会冲过 100%。服务端 `cc-books/books.py` 的 `_json` 里加了 `X-Raw-Length`，并且**必须配 `Access-Control-Expose-Headers`**（工具箱在 tool.* 、书库服务在 cc.* ，跨域自定义响应头不 expose 前端读不到）。测试 `tests/bkdownload.test.js`（10 条，假 fetch、不联网）。
  - **⚠️`Toolbox/server/books.py` 是过期副本，别照它改**（2026-07-30 记）：线上真正在跑的是 `/home/ubuntu/cc-books/books.py`（systemd `cc-books.service`），它比仓库这份多了 `folder` 字段 / `/setfolder` / `X-Raw-Length`。仓库那份留着做参考，**改服务端务必改 `/home/ubuntu/cc-books/books.py` 并 `sudo systemctl restart cc-books`**。
  - **字体没有定时同步**，只有三个触发点：冷启动（`idbInit` 之后）、打开书架（`rbOpenShelf`）、展开字体面板（`readingToggleFontPanel`），且有 4 秒节流。「传了半天另一台设备没有」先问是不是压根没触发，别急着查服务器。`bkSyncCfg()` 缺 url 或 token 时**所有 bkSync* 直接返回、不报错不提示**——书和字体共用这套配置，所以「书架能看到服务器的书吗」是判断配置好没好的最快问法。
  - **删除必须两头都删**：只删服务器，本机 IndexedDB 那份会在下次 `bkSyncPullFonts` 被当成「本地独有」补传回去；只删本机，服务器那份会被当成「新字体」拉回来。两个方向都是「删了又自己回来」。`readingDeleteFontAny` 是唯一同时处理两头（外加清空引用它的槽位）的入口，别绕开它。
