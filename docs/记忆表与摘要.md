# 记忆表格与摘要压缩

> 从 `CLAUDE.md` 拆出的功能笔记（2026-08-06 拆）。**动这块代码之前先整本读一遍**——里面每条 ⚠️ 都是踩过的坑。

- **上下文压缩**（`chatCompressContext`）：对话模式默认 40 条触发、保留 20（设置里「触发」滑块可调）；**翻译/共读固定 10 条触发、保留最近 5 条**（写死保证一致）。滑块在翻译/共读下禁用、显示「10 条（自动）」。

- **摘要（断点续传设计）**：分段存 `chatCompressSummaries`，`chatCompressedCount` 逐段推进；某章总结失败（网络/回空）**就地停住不推进计数**，那章连同后面留作未压缩、下一轮共读自动补上（绝不越过、否则永久跳过）。可在「📋 摘要」弹窗编辑/删除/**♻️单段重新生成**（按 `chatCompressSegEnds` 记的原文范围重切；旧版无范围记录则提示手动补）。记忆表格缺回可「补齐/重建」（只用现有摘要重折、不重读正文）。保存用 `chatSaveCurrentConv(true)`（**没有 `chatSaveConv` 这个函数**；`true` 强制标脏，否则自动生成的摘要不会同步）。

- **⚠️两层记忆的「中间态」段（2026-08-20 修，改这块前必看）**：规矩是「最近 `CHAT_SUMMARY_MAX_SEGS`(=5) 段原样带 + 更早的攒满 3 段折一次进大纲」（`_foldOutline`，大纲为空时阈值降到 1 好立刻重建）。**所以稳态下就有 1-2 段处在「超出 5 段窗口了、但还没攒够 3 段没被折」的中间态**——这是设计，不是没跑。
  - 踩过的坑：发送时写成 `chatCompressSummaries.slice(covers).slice(-5)`，先跳过已折的、再只留最近 5 段，**中间态那几段两头落空**（大纲没覆盖到、发送时又被截掉），那段记忆凭空消失。用户从「7 段摘要、大纲只折入 1 段」的截图看出来的：丢的就是下标 1 那段。
  - **判据是守恒律：「大纲覆盖的段」∪「发出去的段」必须等于全部段。** 只数段数看不出漏没漏中间那段。
  - 现在：走大纲那条路 `slice(chatOutlineCovers)` **全带、不再截**（背景追问 `chatAskBg` 那条路一直就是这么写的，这次才补齐一致）；走记忆表那条路照旧 `slice(-5)`（远期靠四张表兜底，不靠大纲）。另有兜底闸 `> MAX+3` 才截，防「大纲一直生成失败」时上下文无限膨胀。
  - 回归 `tests/outlinegap.test.js`（14 条，含源码断言 H2 专防有人改回旧写法）。

- **翻译剧集记忆（2026-07-16 整轮重构，最终形态）**：`chatMemoryTables` 挂 4 个数据键——**三张展示表** `characters`(人物)/`places`(地点)/`cases`(**文化背景**，就是原「案件/剧情线」改名，key 没动) + **前情** `recap`。`terms`(译名)/`settings`(设定) 两表已废弃、不展示不提取，旧数据在提取重建时**原样保留不销毁**（可反悔）。列定义 `_mtTransCharCols`/`_mtTransPlaceCols=['地点','说明']`/`_mtTransCaseCols=['线索/事件','进展','关键点','状态']`。
  - **来源分工（关键）**：人物+地点 ← **前情自动提取**；文化背景 ← **追问/记住**。① 追问引擎 `chatTransHarvestMemory` 现只更 `cases`、**就地改不重建对象**（别再整体重建，那会抹掉别的表——recap 就被抹空过一次）。② `chatTransMineCharPlace(recapText)` 从一段前情梗概增量提人物+地点，就地改 characters/places；`chatTransUpdateRecap` 每压完一集自动调它、给该 recap 段打 `_mined`。兜底 `chatTransMineMissing`(找没 `_mined` 的段)/`chatTransMineAll`(逐集补，人物/地点面板顶「🔄 从前情补齐」按钮)。
  - **前情 recap**：数组 `[{text,srcIdx,_mined}]`（旧单块字符串按需迁移，`srcIdx:null` 排最前）。每集一段 `chatTransUpdateRecap(src,manual,srcIdx)`（≈300字/`max_tokens:1100`，按 srcIdx 去重、加完 sort）；自动压上一集 `chatTransUpdateRecapFromPrev`（`_recapped` 防重）、手动「压缩本集」`chatTransRecapCurrent`、批量「补齐前 N 集」`chatTransRecapAll`。显示复用摘要段 `_segHtml`（折叠+字数+🗑删+♻️重做）。
  - **⚠️逐段翻译不再回喂「文化背景」表（2026-08-08 用户选精简）**：`chatTransMemoryPromptBlock(includeCases)` 新增参数，**默认 `true`（追问照旧全量）**，`translateRunSelected` 传 `false` → 翻译只带人物+地点。为什么砍这张而不是别的：这块是**每翻一段就整个重发一遍**的，三张表里只有 `cases` 会一路膨胀（数据来自追问 `chatTransHarvestMemory`，追问越多攒越多；人物/地点收敛在剧中固定那些人和地方），而它列的是**剧情线**、对逐段译文准确性帮助最小（翻译指令里本来就写着「不要在译文里额外复述这些背景」）。人物表是「说话人标真名/人称性别不跳/译名统一」的命根子，地点表只有 2 列很短，都留着。实测 12 人物 /8 地点 /25 条背景的样本：每段少发 1641 字、省 60%。⚠️**提示语必须跟着按「实际发出去的表」拼**——不带 cases 时那句「结合文化背景理解剧情」要一起撤掉，否则是让模型参考一张根本没收到的表。
  - **⚠️前情不再喂 AI**（用户 2026-07-16 选省额度）：`chatTransRecapJoin` 已从追问 `translateAskRun` 移除。跨集信息全靠三张表（`chatTransMemoryPromptBlock` 回喂人物/地点/文化背景）；前情只作「给人读 + 提人物地点的原料」。本集内语境靠 `translateAskRun` 里 userMsg 的「本集前文」（预算 `CTX_CHAR_BUDGET=200000`，用户选保持整段）。
  - **人物/地点提取＝增量省 token（2026-07-19）**：`chatTransMineCharPlace(recapText,signal)` 现让模型只吐「新增/有变化的行」（`max_tokens:2000`），客户端 `_transUpsertRows` 按名字 upsert 合并（非空字段覆盖、空字段留旧、旧行不动）；给动过的行打 `_chg='new'`(绿点)/`'upd'`+`_prev`(橙点)，每次提取先清上批标记。「🔄 从前情补齐」`chatTransMineAll` 有停止键（`chatTransMineStop`：`chatTransMineAbort`+`chatTransMineCtl.abort()`）；`chatStreamChatBigOutput` 遇 AbortError 不再降档重试。

- **共读/阅读记忆表格＝增量+删除省 token（2026-07-19）**：四张表（人物/地点/年表/主线）的**自动增量**更新（共读 `_updateMemoryTables`、阅读 `readerUpdateMemoryTables` 的非 rebuild 分支）改用 `_MT_SYS_PROMPT_DELTA`——模型只吐「增改行 + 【删除】清单」（`max_tokens:50000` 保持高位——省 token 靠模型少吐、不靠改上限；上限调低反而会截断首次建表/大批量的后半张表），共享引擎 `_mtApplyDelta(result,tables)` 就地并进：`_mtUpsertRows`(按 `_mtRowKey` 主键 upsert+打绿/橙点) + `_mtDeleteByKeys`(删除清单显式删行，人物/地点按名、年表/主线按事件) + `_mtParseDeletions`(解析【删除】小节)。⚠️**删除必须显式**（增量里「省略」＝没变，不再等于删除）。⚠️**「本批无更新」是正常态**，只要 `_mtDeltaLooksValid(result)` 就推进水位/upTo（否则会永远重喂）；真·空/乱码才不推进、下轮重试。**手动「补齐/重建」(`chatRebuildMemTables`/`readerUpdateMemoryTables(rebuild=true)`) 仍走整表 `_MT_SYS_PROMPT`**（权威重折，需要吐全表）。测试 `test_mt_delta.js`。

- **名单（人名/地名高亮）云同步（2026-07-27 加）**：用户报「设置里名词的名单好像不太会同步」——**不是偶发，是压根没进同步**：`reading_names_*` 从来没挂进 `cfBuildManifest`。而且**光挂上去也没用**：它原本按 `readerBookId` 存，而书 id 是 `bk_<时间戳>_<随机>`、**每台设备导入时各生成一个**，同一本书在手机和电脑上 id 不同，同步过去对不上号。所以键改成跨设备稳定的 **fileKey(`书名|字节数`)**（书签/划线早有先例：`readingMarksConvId()` 就是干这个的）。配套三件：① `_readingNamesMigrate(newKey)` 打开某本书时把旧键（书 id / `reader_书id`）搬过来并删旧；② `_readingNamesSweep()` 打包前全量扫一遍，把**没打开过的书**也搬了，否则推上云全是死键（幂等，书没加载完会重置标志等下次）；③ 落盘统一走 `_readingNamesWrite`（打 `reading_names_ts` + 3 秒防抖推云）。同步语义照抄书名/书籍类型：**整块按时间戳后写覆盖**（`readingNamesApplyAll` 先清本地所有名单键再写云端那份——不清就成了只增不删，别的设备删掉的名字会在这台机器复活）。⚠️`reading_names_on`(高亮总开关) 和 `reading_names_ts` 前缀一样，打包和清理时**都必须排掉**。测试 `tests/names.test.js`（18 条）。
